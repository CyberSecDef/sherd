# ADR 0004: Frontmatter round-trip by surgical byte splice

- **Status:** Accepted
- **Date:** 2026-08-21
- **Decides:** `OD-004`
- **Affects:** `FR-MD-033`, `FR-MD-030`…`FR-MD-035`, `FR-BASE-007`, `PLAN.md` P0.2, P4.5

## Decision

Granite will **never re-serialize a frontmatter block it did not need to change.**
Writing a property parses the YAML only to locate that property's value, then
splices new bytes into that range. Every other byte of the file — comments,
alignment, quoting style, blank lines, key order — is carried through
untouched because it is never rewritten.

We will **not** adopt a YAML library's node round-trip (`gopkg.in/yaml.v3`) or
a comment-aware marshaller (`github.com/goccy/go-yaml`) as the write path.

## Context

`FR-MD-033` is stated in the specification as non-negotiable, and unusually
for that document it names the reason: round-trip mangling "is a top user
complaint in this category". Design principle 5 says the same thing more
broadly — the app never rewrites a file the user did not edit.

The failure this prevents is quiet and cumulative. A user hand-aligns their
frontmatter, adds a comment explaining why a property is set the way it is, and
Granite silently reformats all of it the first time a plugin touches one
unrelated key. Nothing errors. The user notices weeks later, in a Git diff,
and stops trusting the tool with their files.

Any approach that decodes the whole block and re-encodes it is fighting to
reproduce the input exactly. The surgical approach does not have to reproduce
anything: it does not touch what it does not change.

## Options considered

### Option A — `gopkg.in/yaml.v3` Node API
Decode to `yaml.Node`, mutate, re-encode. The documented approach for
structure preservation, and the one the specification suggested prototyping.

### Option B — `github.com/goccy/go-yaml`
A modern YAML library that advertises comment support.

### Option C — Surgical byte splice
Parse only to locate. `yaml.Node` carries `Line`/`Column`, which is enough to
find a value's start; the value's extent is then computed and those bytes
replaced. The document is never re-encoded.

## Evidence

200-fixture corpus in `spikes/od004-frontmatter/testdata/`, generated by
`gen_fixtures.go`. It is deliberately hostile: head/inline/foot comments, three
quoting styles, aligned values, blank lines, block scalars (`|`, `>`, `|+`,
`|-`), flow and block sequences, nested maps, anchors and merge keys, YAML 1.1
booleans, nulls, dates, CJK and RTL text, CRLF, tabs, trailing whitespace, and
a realistic Granite note.

```sh
cd spikes/od004-frontmatter && go test ./... -v
```

**Read a file, write it back unmodified.** This is the number that decides it:

| Approach | Byte-exact | Differed |
|---|---|---|
| `gopkg.in/yaml.v3` Node | **63 / 200** (32%) | 137 |
| `goccy/go-yaml` | **4 / 200** (2%) | 196 |
| **Surgical splice** | **200 / 200** (100%) | 0 |

Neither library is close. `yaml.v3` drops comments, normalizes quoting, and
re-indents. `goccy` additionally reorders keys, because its round-trip goes
through a Go map. Both are correct YAML processors and completely unsuitable as
a write path for files a human maintains by hand.

The surgical result is 100% *by construction* rather than by effort, which is
the point: it cannot regress, because there is no reproduction step to get
wrong.

**Change one property, leave everything else alone.** Surgical: 185 of 197
applicable fixtures with zero collateral change. The 12 that were not clean are
all one bug in the prototype's extent calculation, not a flaw in the approach:

| Shape | Count | Cases |
|---|---|---|
| Block scalar (`|`, `>`, `|+`, `|-`) | 4 | value spans lines the prototype miscounts |
| Nested map / block sequence | 4 | same cause |
| Anchor and merge key | 1 | same cause |
| Blank line or comment at block edge | 3 | boundary off-by-one |

The prototype bounds a value by "the line before the next top-level key", which
is wrong whenever a value is itself multi-line. `yaml.Node` exposes a start
position but no end position, so P0.2 must compute the extent directly. That is
a known, bounded piece of work, not a research risk.

## Consequences

**Accepting this means:**
- `pkg/format` needs a YAML *extent scanner*: given a parsed document and a key,
  return the exact byte range of its value, correct for block scalars, nested
  collections, flow collections, anchors, and comments. This is the real work
  of P0.2, and it is now precisely scoped.
- Reads and writes are asymmetric: `yaml.v3` (or any conformant parser) is fine
  for *reading* values into typed properties. Only the write path is surgical.
- Inserting a new key, or deleting one, is a separate operation from updating
  one, and each needs its own placement rule (where does a new key go, and what
  happens to surrounding blank lines).
- `FR-BASE-007` — editing a cell in a Bases view writes through to frontmatter —
  gets this guarantee for free, and P4.5 must route through this single writer
  rather than growing a second one.

**We are giving up:**
- The convenience of `yaml.Marshal`. Every frontmatter mutation is a deliberate,
  positioned edit. This is more code and it is the correct amount of code.

## Reversal cost

**Low to moderate.** The approach is contained behind the frontmatter writer in
`pkg/format`; callers ask to set a key and do not know how it happens. Swapping
in a library round-trip later would be a single-package change.

The cost is not in the code, it is in the files: once users have vaults whose
formatting Granite has preserved for a year, adopting a normalizing writer would
rewrite every frontmatter block in every vault on first touch. That is
effectively unshippable, which means this decision is *practically* permanent
even though it is *technically* cheap to reverse. Decide it once, here.
